## 1. 프로젝트 개요

### 1.1 프로젝트 정의

본 프로젝트는 다양한 AI 모델과 에이전트를 통합하고, 여러 기기에서 동일한 작업 세션을 이어갈 수 있는 **개인용 AI 워크스페이스**를 구축하는 것을 목표로 한다.

Mac mini를 상시 실행 서버로 활용하는 방안을 우선 검토하며, MacBook·모바일·웹에서 동일한 작업 환경에 접근할 수 있도록 한다.

일반적인 AI 채팅 기능을 제공하는 동시에 다음 기능을 통합한다.

- 기기 간 지속적인 세션 관리
- 멀티 LLM 및 사용자 정의 Agent
- 재사용 가능한 하네스·메모리 템플릿
- 예약 메시지 및 반복 루틴
- AI의 파일·도구 실행과 결과 관리
- 로컬 AI 모델과 외부 AI API의 혼합 운용

**본 프로젝트는 독립적인 AI 비서를 완성하는 작업이 아니다.** 향후 개인 AI 비서를 구축할 때 재사용할 수 있는 세션 관리, 모델 실행, 메모리, 자동화 인프라를 먼저 구현하는 단계다.

### 1.2 장기적인 방향

프로젝트 발전 방향은 다음과 같다.

**1단계 — Personal AI Workspace (현재 프로젝트)**

기기 간 세션 연속성, 멀티모델, 메모리 템플릿, 예약 실행 등 개인용 AI 실행 기반 구축.

**2단계 — Personal AI Assistant (향후 프로젝트)**

구축한 인프라를 활용해 사용자 상황과 일정에 따라 능동적으로 행동하는 개인 AI 비서 구현.

최종적으로는 사용자가 어떤 기기를 사용하든 AI가 이전 작업과 문맥을 유지하고, 지정된 작업을 적절한 모델과 실행 환경에서 수행하는 시스템을 지향한다.

## 2. 문제 정의

### 2.1 기존 AI 도구의 한계

현재 Claude Code, Codex, Cowork 등 다양한 AI 실행 환경을 사용하더라도 다음과 같은 문제가 발생할 수 있다.

**문제 A — 실행 환경과 세션의 결합**

맥북과 맥 미니 사이에 프로젝트 디렉터리가 동기화되어 있더라도, 파일만 동일할 뿐 실행 중인 프로세스·세션 상태·도구 호출 기록이 자동으로 공유되지는 않는다.

일부 기존 도구가 원격 세션 접속이나 handoff를 지원하지만, 서로 다른 모델 및 도구를 아우르는 독립적인 세션 관리 환경은 별도로 필요하다.

**문제 B — AI 모델과 도구의 분산**

GPT, Claude, DeepSeek, Ollama 등을 사용하려면 서비스마다 인터페이스, 대화 기록, 도구 설정을 별도로 관리해야 한다.

**문제 C — 반복적인 초기 환경 설정**

새 대화나 프로젝트를 시작할 때 시스템 프롬프트, 개발 규칙, 메모리, 스킬, 사용 가능한 도구 등을 반복해서 설정해야 한다.

**문제 D — 자동화와 채팅의 분리**

예약 메시지, 반복적인 자료 조사, 모니터링, 백그라운드 작업 등을 일반 대화 및 에이전트 실행 환경과 일관되게 관리하기 어렵다.

### 2.2 해결 방향

기존 도구를 각각 대체하는 것이 아니라, **세션·메모리·에이전트·자동화를 통합 관리하는 공통 실행 플랫폼**을 구축한다.

특히 다음 두 개념을 분리한다.

- **접속 환경:** 사용자가 AI와 상호작용하는 기기 및 인터페이스
- **실행 환경:** AI가 모델을 호출하고 명령어를 실행하며 파일을 수정하는 실제 컴퓨터 또는 런타임

이 둘을 분리하여 접속 기기가 바뀌어도 작업을 지속할 수 있는 구조를 만든다.

## 4. 핵심 기능 상세 명세

### 4.1 F-01. 기기 간 세션 연속성

**우선순위: P0 — 프로젝트의 핵심**

#### 목표

기기를 변경해도 동일한 대화, 작업 상태, 실행 환경에 접근할 수 있도록 한다.

#### 필수 기능

1. 서버에 영구적인 Session ID 발급 및 저장
2. 세션별 대화 기록 보존
3. 세션과 작업 디렉터리 연결
4. Agent 실행 상태 및 이벤트 기록
5. 사용 기기가 변경되어도 동일한 세션에 재접속
6. 진행 중인 작업의 로그 및 결과 조회
7. 연결이 끊어졌을 때 세션을 보존하고 재접속 시 상태 복원

#### 구분해야 할 상태

**Conversation State**
- 메시지
- 모델 정보
- 대화 요약
- 도구 호출 이력

**Workspace State**
- 프로젝트 경로
- Git 브랜치 및 변경 사항
- 작업 디렉터리
- 프로젝트 설정

**Execution State**
- 실행 중인 작업
- 명령어와 작업 결과
- 승인 대기 상태
- 작업 로그 및 종료 상태

**Agent State**
- 사용 모델
- 적용된 하네스
- 사용 가능 도구
- 메모리 연결 정보

#### 기술적 제약

파일 동기화와 실행 세션 동기화는 별개다.

따라서 초기에는 Mac mini의 중앙 실행 환경을 유지하고, 각 기기에서는 해당 환경에 접근하는 방식을 우선 검토한다.

실행 중인 프로세스를 다른 컴퓨터로 직접 이전하거나, 서로 다른 AI 모델 사이에 비공개 내부 추론 상태를 그대로 넘기는 기능은 보장하지 않는다.

---

### 4.2 F-02. 멀티 LLM 및 Agent 관리

**우선순위: P1**

#### 목표

하나의 인터페이스에서 외부 API 모델 및 로컬 모델을 선택하고, 사용자 정의 Agent를 구성한다.

#### 지원 대상

초기 연동 후보:
- OpenAI API
- Anthropic API
- DeepSeek API
- Ollama

추후 다른 모델 공급자를 추가할 수 있도록 확장 가능한 인터페이스를 설계한다.

#### Agent 설정 항목

- Agent 이름 및 역할
- 사용 모델
- 시스템 프롬프트
- 허용 도구
- 메모리 접근 범위
- 작업 승인 정책
- 모델 추론 및 생성 설정

#### 멀티에이전트 운영

초기에는 수동 Agent 선택을 기본으로 한다.

이후 필요에 따라 작업별 라우팅, 보조 Agent 호출, Agent 간 작업 위임을 추가한다.

모든 요청을 여러 Agent에게 무조건 전달하는 방식은 기본 정책으로 채택하지 않는다.

효율성은 실제 비용·응답 시간·작업 성공률을 비교해 검토한다.

---

### 4.3 F-03. 하네스 및 메모리 템플릿

**우선순위: P1**

#### 목표

사용자가 사전에 정의한 실행 환경을 새 세션에서 재사용하도록 한다.

#### 하네스 템플릿 구성

- 기본 시스템 지침
- 사용할 모델 및 Agent 설정
- 사용 가능 도구
- 스킬 및 작업 규칙
- 파일 접근 권한
- 승인 정책
- 사용할 메모리 범위

#### 메모리 범위

**Global Memory**

사용자가 모든 세션 또는 지정된 프로필에서 공통으로 사용하도록 허용한 정보.

**Profile Memory**

개발, 일반 대화, 리서치 등 작업 성격별 공통 지침.

**Project Memory**

특정 프로젝트의 구조, 설계 결정, 요구사항, 작업 이력.

**Session Memory**

현재 세션에서 발생한 대화, 진행 상황, 작업 결과.

#### 주요 원칙

- 메모리를 단순히 전체 대화에 복사해 넣지 않는다.
- 필요한 정보를 선택적으로 검색하여 주입한다.
- 서로 다른 프로젝트의 정보가 무분별하게 섞이지 않도록 한다.
- 템플릿 수정 시 기존 세션에 적용할지 정책을 정한다.
- 메모리 작성·수정·삭제 내역의 추적 가능성을 검토한다.

초기 구현에서는 명시적으로 저장한 메모리를 우선하며, 자율적 메모리 생성은 후속 단계에서 검토한다.

---

### 4.4 F-04. 예약 메시지 및 루틴

**우선순위: P1**

#### 목표

사용자가 접속하지 않은 상태에서도 미리 등록한 메시지 및 AI 작업을 실행한다.

#### 기능 구분

**예약 메시지**

지정된 시각에 메시지 또는 알림을 전달한다.

**반복 예약**

매일, 매주 또는 사용자가 지정한 반복 일정에 따라 실행한다.

**예약 Agent 작업**

특정 시각에 Agent를 실행해 조사, 정리, 분석 등의 작업을 수행한다.

**루틴**

여러 단계의 작업을 하나의 재사용 가능한 워크플로로 정의한다.

**조건부 알림**

지정된 조건이 충족되었을 때 알림을 발생시킨다. 구체적인 조건 평가 방식은 추후 결정한다.

#### 예시

AI 채용 공고 모니터링 루틴:

1. 예약 시각에 실행
2. 지정된 채용 사이트 및 데이터 소스 조사
3. 기존 결과와 비교
4. 새 공고에 대한 적합도 분석
5. 결과 저장
6. 신규 공고가 있을 경우 알림

#### 필수 운영 사항

- 예약 작업 저장 및 수정
- 실행 이력 관리
- 실패 감지 및 재시도
- 중복 실행 방지
- 작업 취소 및 중지
- 사용자 시간대 처리
- 알림 채널 설정

루틴은 채팅 세션과 독립적으로 실행할 수 있어야 하지만, 실행 결과를 관련 세션이나 프로젝트에 연결할 수 있도록 설계한다.

---

### 4.5 F-05. 원격 작업 실행 및 권한

**우선순위: P1**

#### 목표

AI가 허용된 작업 환경에서 파일을 읽고, 명령어를 실행하고, 실행 결과를 사용자에게 전달한다.

#### 기능

- 파일 조회 및 수정
- 터미널 명령 실행
- Git 작업
- 작업 결과 및 로그 스트리밍
- 위험 작업에 대한 사용자 승인
- 로컬 및 원격 Worker 관리

원격 Worker는 Mac mini에서 접근할 수 없는 MacBook 전용 리소스나 개발환경을 활용할 때 필요하다.

초기에는 중앙 호스트 실행을 우선하고, 원격 Worker 도입 범위는 실제 사용 사례로 검증한다.

## 5. 시스템 아키텍처 초안

**현재 단계: 개념 아키텍처 / 미확정**

### 5.1 전체 구조

**Client Layer**

MacBook Web/PWA, Mobile Web/PWA, Browser

↓

**Secure Network Layer**

Tailscale, 인증 및 접근 제어

↓

**Application Server**

- Session Manager
- Conversation API
- Agent Router
- Template Manager
- Memory Manager
- Scheduler
- Notification Manager

↓

**Execution Layer**

- LLM API Provider
- Ollama Local Runtime
- Coding Agent Runtime
- Tool Executor
- Local / Remote Worker

↓

**Storage Layer**

- 대화 및 작업 상태 DB
- 사용자 정의 프로필 및 템플릿
- 메모리 및 문서 인덱스
- 작업 로그
- 파일 및 아티팩트 저장소

### 5.2 핵심 엔터티 초안

| 엔터티 | 책임 |
|---|---|
| Workspace | 프로젝트와 관련 리소스의 논리적 묶음 |
| Session | 대화와 작업의 연속성을 나타내는 단위 |
| Execution | 개별 Agent 또는 도구 작업 실행 |
| AgentProfile | 모델·역할·도구·권한 설정 |
| HarnessTemplate | 재사용 가능한 실행 환경 정의 |
| MemoryEntry | 공통·프로젝트·세션별 기억 |
| Worker | 명령 및 파일 작업을 수행하는 실행 호스트 |
| ScheduledTask | 예약 메시지 및 반복 작업 |
| RunHistory | 실행 결과, 상태, 오류 및 감사 이력 |

초기 데이터 모델 설계 시 Session과 Execution을 반드시 분리한다.

하나의 Session에는 여러 Execution이 존재할 수 있으며, 세션이 종료되지 않아도 개별 실행은 완료·실패·취소될 수 있다.

### 5.3 주요 설계 원칙

1. **Server as Source of Truth**  
   중앙 서버가 세션과 작업 상태의 기준이 된다.

2. **Client / Execution Separation**  
   접속 기기와 실제 실행 기기를 분리한다.

3. **Provider Independence**  
   특정 AI 공급자에 종속되지 않는 모델 연결 계층을 구성한다.

4. **Reusable Configuration**  
   공통 하네스와 메모리 구성을 템플릿화한다.

5. **Persistent Execution Records**  
   실행 이력과 결과를 세션 외부에 영구 저장한다.

6. **Permission by Default**  
   Agent에 필요한 최소 권한만 부여한다.

## 8. MVP 범위 및 개발 단계

### Phase 0 — 사전 검증 및 기술 결정

**목표:** 기존 오픈소스로 해결 가능한 범위를 파악한다.

주요 작업:

- Happier의 기기 간 세션 연속성 테스트
- OpenCode Server API 및 세션 구조 분석
- Ollama와 외부 API 연동 방식 검토
- 자체 개발과 Fork 방식 비교
- 중앙 실행 방식과 원격 Worker 방식 검증
- 보안 및 라이선스 검토

**완료 기준:** 기술 선택 근거와 최소 아키텍처 확정.

### Phase 1 — Core Workspace MVP

**목표:** 기기 간 동일 세션 이어하기 구현.

구현 범위:

- 기본 웹 채팅 UI
- 서버 기반 세션 생성·저장·조회
- 대화 및 작업 이벤트 실시간 동기화
- 중앙 실행 환경
- MacBook / 모바일에서 재접속
- Tailscale 연결
- 최소한의 인증 및 권한 제어

**핵심 성공 시나리오:**

MacBook에서 작업 세션을 생성하고 작업을 시작한다. MacBook을 닫고 모바일에서 해당 세션에 접속한다. 이전 메시지 및 실행 상태를 확인하고 추가 지시를 전달한다. 이후 다시 MacBook에서 동일한 세션을 열어 작업을 이어간다.

이때 작업 프로세스는 중앙 실행 환경에서 유지된다.

### Phase 2 — Multi-Model & Template

**목표:** 사용자 지정 모델 및 환경 구성 지원.

구현 범위:

- 외부 API 연결
- Ollama 연동
- Agent 프로필
- 하네스 템플릿
- 공통 및 프로젝트 메모리
- 세션 생성 시 템플릿 선택

**완료 기준:** 동일한 템플릿을 서로 다른 세션에 재사용할 수 있고, API 및 로컬 모델을 선택적으로 사용할 수 있다.

### Phase 3 — Agent Execution

**목표:** 실제 개발 작업이 가능한 AI 워크스페이스로 확장.

구현 범위:

- 파일 및 터미널 도구
- Git 연동
- 장시간 실행 작업
- 명령 승인 및 작업 취소
- 원격 Worker 검토·도입
- 실행 로그와 변경 사항 추적

**완료 기준:** AI가 실제 프로젝트 작업을 수행하고, 사용자는 다른 기기에서 상태 및 결과를 확인할 수 있다.

### Phase 4 — Scheduled Tasks & Routines

**목표:** 능동적으로 작업을 실행할 수 있는 기반 구축.

구현 범위:

- 일회성 예약 메시지
- 반복 예약
- 예약 Agent 실행
- 루틴 정의 및 실행
- 실행 이력
- 알림 및 오류 처리

**완료 기준:** 사용자가 접속하지 않아도 예약된 AI 작업이 실행되며, 결과를 나중에 확인하거나 알림으로 받을 수 있다.

## 9. 비기능 요구사항

### 9.1 지속성

- 클라이언트 종료가 서버 작업 중단을 의미하지 않아야 한다.
- 저장된 대화와 실행 이력은 서버 재시작 이후에도 조회할 수 있어야 한다.
- 실행 중 호스트가 재부팅되는 경우의 복구 가능 범위를 명확하게 정의한다.

### 9.2 보안

- 기본적으로 Tailscale을 통한 비공개 접속을 지향한다.
- Tailscale 연결과 별도로 애플리케이션 인증을 적용한다.
- API Key와 인증 정보는 클라이언트에 노출하지 않는다.
- 파일 및 Shell 접근에 권한 정책을 적용한다.
- 위험한 작업은 사용자 승인을 요구한다.
- 외부 입력과 검색 결과가 Agent의 권한을 변경하지 못하도록 설계한다.
- 원격 실행의 권한 범위를 호스트별로 분리한다.

### 9.3 비용 및 성능

- 모델별 요청 및 사용량 기록
- 응답 지연시간 측정
- 로컬 모델과 외부 API 실행 비용 비교
- 불필요한 다중 Agent 호출 최소화
- 메모리 검색 및 프롬프트 길이 최적화

### 9.4 관측 가능성

- 세션 상태
- Agent 실행 흐름
- Tool 호출 기록
- 오류 및 재시도
- 예약 작업의 실행 결과

위 정보를 사용자가 확인할 수 있어야 한다.

6. 기능 구현 후에는 실제 기기 간 시나리오로 검증한다.
7. AI 비서로의 확장 가능성을 고려하되 초기 범위를 유지한다.

### 14.3 최초 수행 작업

Work 프로젝트에서 가장 먼저 수행할 작업은 다음과 같다.

**Task 1. 오픈소스 심층 조사**

Happier, OpenCode, OpenHands, Letta Code, OpenClaw의 아키텍처와 확장 가능성을 조사한다.

**Task 2. 핵심 세션 PoC**

Mac mini에서 시작한 작업에 MacBook과 모바일이 접속하는 최소한의 시나리오를 구현하거나 기존 오픈소스로 검증한다.

**Task 3. 아키텍처 선택**

Fork / 자체 개발 방식 및 실행 런타임을 결정하고 근거를 문서화한다.

**Task 4. 상세 설계 작성**

최종 선택한 구조를 기준으로 데이터 모델, API, 세션 생명주기, Worker 통신 및 보안 정책을 구체화한다.

이후 Phase 1 MVP 개발로 진입한다.

## 15. 최종 방향 요약

본 프로젝트의 핵심은 새로운 챗봇을 하나 더 만드는 것이 아니다.

**여러 기기에서 동일한 작업을 지속하고, 다양한 AI 모델과 에이전트가 공통 세션·메모리·실행 인프라를 활용할 수 있도록 하는 개인용 AI 플랫폼을 구축하는 것이다.**

프로젝트의 우선순위는 다음과 같다.

1. 지속적인 세션 및 실행 환경
2. 멀티 LLM 및 사용자 정의 Agent
3. 재사용 가능한 하네스와 메모리
4. 예약 메시지 및 자동화 루틴

이 네 가지를 완성한 이후, 향후 개인 AI 비서가 사용할 기반 인프라로 확장한다.

**현재 가장 먼저 검증할 가설은 ‘중앙에서 관리되는 AI 세션과 실행 환경을 통해, 사용 기기에 관계없이 작업을 이어갈 수 있다’는 것이다.**

이 가설을 검증하는 것이 프로젝트의 첫 번째 개발 목표다.
