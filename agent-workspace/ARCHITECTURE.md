# 아키텍처

갱신일: 2026-10-28. 상태: **제품·실행 경계 일부 확정 / 구현 구조 초안**.

[현재 요구사항](REQUIREMENTS.md)과 [의사결정 기록](DECISIONS.md)을 기준으로 한다. [PRD §5](PRD.md)는 최초 개념 초안이다.

## 확정된 배치와 책임

```text
MacBook / 모바일
       │ 같은 서비스에 접속 (Tailscale + 애플리케이션 인증)
       ▼
Mac mini
├── 자체 사용자 환경과 애플리케이션 서비스
├── 대화·작업·실행·승인·결과 상태 저장
└── 프로젝트 저장소 (iCloud 밖)
    ├── 작업 A: 브랜치 A + worktree A
    └── 작업 B: 브랜치 B + worktree B
       │
       └── Git/GitHub로 코드 변경 공유·통합
```

접속 기기가 바뀌어도 같은 중앙 상태를 조회한다. 클라이언트 종료로 서버 작업이 종료되지 않아야 한다. GitHub는 코드 공유를 담당하며 대화·승인·실행 상태를 동기화하는 수단으로 사용하지 않는다.

## 확장성을 위한 설계 기준

아래는 DEC-011을 구체화한 설계 기준이며 인터페이스의 실제 규격은 상세 설계에서 정한다.

- 사용자 화면·프로젝트 운영·설정 저장과 특정 실행 엔진의 API를 분리한다. OpenCode를 우선 검증하되 화면과 업무 규칙에 해당 엔진의 규격을 직접 고정하지 않는다.
- 자체 작업·세션 식별자와 외부 엔진 식별자를 구분한다. 기존 대화·실행 기록을 유지하면서 새 엔진을 연결할 수 있게 한다. 엔진 내부 실행 상태의 무손실 이전까지 가정하지 않는다.
- 프롬프트·모델·스킬·도구·메모리·권한을 자체 템플릿으로 표현하고, 연결 계층에서 엔진별 설정에 대응한다. 지원 범위·버전·적용 결과를 명시한다.
- 권한 판단과 승인 기록은 교체 후에도 같은 제품 정책을 유지해야 한다. 지원되지 않는 권한 제한을 조용히 생략하지 않는다.
- 메모리 선택·검색과 실행 시 주입을 분리하고, 엔진 내부 메모리와 자체 저장 기록의 역할을 구분한다.
- 현재 실행 단위를 향후 여러 단계의 작업 순서나 원격 Worker에서 호출할 수 있게 작업·실행·호스트 경계를 분리한다. 초기에는 Mac mini에서 실행한다.
- 저장 구조와 템플릿 변경 시 버전·이전 경로를 마련해 기존 사용자 데이터와 설정을 보존한다.

확장성은 실제 필요한 연결 경계부터 구현하고 문서·검증으로 확인한다. 첫 버전의 기능 범위 내 안정성·복구·백업은 출시 기준에 포함한다.

## 하네스 범위와 검증 순서

첫 버전은 프롬프트·모델·스킬·도구·메모리·권한 설정과 템플릿 재사용을 제공한다. 사용자 정의 작업 순서 구성은 후속 확장이다. [하네스 템플릿 명세](specs/harness-templates.md)를 참고한다.

첫 실행 엔진 검증 대상은 OpenCode다 (DEC-010). 실제 기능·권한·상태 복원·설정 적용을 검증한 뒤 채택 여부를 결정한다. 현재 PoC는 미수행이다.

## 실행 연결 구조 제안 — 검증 필요

자체 서비스가 프로젝트·사용자 세션·작업 기록을 관리하고, 실행 연결은 두 종류로 구분하는 안을 검증한다.

| 연결 유형 | 책임 |
|---|---|
| 모델 API·Ollama | 모델 호출에 더해 파일·명령·도구 실행 흐름을 수행할 런타임을 구성 |
| 기존 Agent 도구 | 해당 도구의 런타임에 지시하고 이벤트·승인·변경·결과를 자체 화면에 연결 |

연결별 지원 기능을 명시해야 한다. 추가 지시, 재개, 중단, 승인, 메모리 적용이 모든 도구에서 동일하다고 가정하지 않는다. 자체 세션 ID와 외부 도구 세션 ID를 연결하는 방식, 대화·이벤트 보존 범위는 상세 설계에서 정한다.

구독 도구는 공식 연동 경로를 우선 검증한다. Codex app-server는 조사 후보이며 채택 결정은 아니다. 대화 중 공식 문서에서 기능을 확인했지만 실제 계정 인증·작업 실행 PoC는 수행하지 않았다.

- [Codex 통합 방식](https://developers.openai.com/blog/codex-as-a-platform)
- [ChatGPT 플랜과 Codex app-server 연결](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

문서 확인일: 2026-10-28. 계정별 접근 권한·제한은 실제 검증 대상으로 남긴다.

## 작업과 Git 구조

작업별 브랜치와 worktree 사용은 확정이다. 아래 논리 관계는 구현을 위한 제안이며 정확한 데이터 모델은 미정이다.

- 프로젝트는 저장소와 실행 위치를 연결한다.
- 개발 작업은 브랜치·worktree와 관련 대화·실행을 연결한다.
- Session과 Execution은 분리한다. 한 대화에 여러 실행이 발생할 수 있다.
- 작업과 대화의 개수 관계, 실행 재개 시 worktree 재사용 규칙은 후속 결정한다.

worktree는 Git 이력을 공유하지만 작업 파일은 분리한다. 다른 브랜치의 변경은 merge/rebase 등 명시적인 Git 작업을 통해 반영하며, 정책은 아직 미정이다. 포트·DB·권한·프로세스는 worktree만으로 분리되지 않으므로 별도 설계가 필요하다.

## 추가 지시와 중단 제어

일반 메시지와 중단 요청을 서로 다른 동작으로 처리한다 (DEC-007). 일반 메시지를 받으면 현재 실행을 유지하며 추가 지시를 전달한다. 실행 중 지시 반영이 불가능한 연결은 대기열을 사용하고, 자체 화면에 전달·대기·반영 상태를 표시한다.

중단 버튼은 별도 실행 제어 경로로 처리한다. 중단 요청 접수와 런타임의 실제 중단 완료를 구분한다. 메시지·실행 식별자, 순서 보장, 중복 전달 방지, 중단 시 하위 프로세스와 대기 지시 처리 및 재개 방식은 상세 설계 대상으로 남긴다.

## Git 자동화 및 승인 경계

작업 브랜치의 커밋·push는 자동 수행하고, 최종 병합은 사용자 승인 후에만 진행한다 (DEC-006). 자체 화면에서 작업 브랜치의 변경과 테스트 결과, 커밋·push 성공 여부 및 병합 승인 대기를 확인할 수 있도록 설계한다.

커밋·push 주기, PR 생성 여부, 병합 방식, 승인 이후 변경이 발생한 경우의 처리 규칙은 미정이다. push 실패와 작업 완료, 병합 완료를 별도 상태로 표현하는 방안을 상세 설계에서 검토한다.

## 의존성 설치 권한

프로젝트 내부 의존성 설치는 자동, 전역 설치·시스템 변경은 사용자 승인 대상으로 구분한다 (DEC-008). 이 정책을 런타임별 권한 설정·승인 이벤트와 연결한다. 프로젝트 경로에서 명령을 시작했다는 사실만으로 변경 범위가 프로젝트 내부라고 판단하지 않는다. 설치 스크립트와 캐시 경로를 포함한 권한 집행 방식은 검증 대상으로 남긴다.

## 최초 설계에서 유지할 원칙

- 중앙 서버를 세션과 작업 상태의 기준으로 삼는다.
- 실행 이력과 결과를 영구 저장한다.
- 모델 공급자 교체와 설정 재사용을 고려한다.
- Agent에는 필요한 최소 권한을 부여한다.
- 모델 호출, 작업 실행, 상태 저장의 경계를 분리한다.
- 향후 다른 호스트의 Worker, 예약·루틴 및 일반 비서 기능을 추가할 수 있게 한다.

## 상세 설계 대기 항목

- OpenCode 검증 버전·모델·인증과 최종 채택 판단, 기존 구독 도구 연결 방식
- 명령 승인, 추가 지시, 중단 및 재접속 상태 전이
- 브랜치 기준점, 자동 커밋·push 시점, 병합 승인 세부 절차, 충돌 해결과 통합 테스트
- 포트·테스트 데이터·공유 자원 및 동시 실행 수 관리
- worktree 종료·보존·삭제 규칙과 미커밋 변경 보호
- 데이터 모델, 저장 기술, 인증·권한, 재시작·백업·복구
