## DEC-001 — 자체 환경 중심, 기존 도구 연결 병행

- 날짜 / 상태: 2026-10-28 / 확정
- 결정: 자체 화면·대화·프로젝트 관리를 중심으로 구축하고, 외부 API·Ollama와 월 구독형 기존 AI 도구를 연결한다.
- 검토한 방향: 기존 도구 통합 중심, 자체 환경 중심, 자체 환경과 기존 도구 연결 병행.
- 근거: 사용자 고유 환경을 유지하면서 이미 구독 중인 도구도 활용하려는 요구.
- 제약: 자체 환경이 모든 Agent 실행 엔진의 자체 구현을 뜻하지는 않는다. 연결 도구의 지원 기능은 각각 검증해야 한다.
- 미결정: 최초 지원 도구, 구독 인증 및 연결 방식, 기존 세션 가져오기 범위. 화면 자동 조작은 확정하지 않았다.

## DEC-002 — 첫 버전은 개발 작업 전체 흐름 우선

- 날짜 / 상태: 2026-10-28 / 확정

- 근거: 실제 기능 구현과 버그 수정이 안정적으로 작동해야 한다는 사용자 요구.
- 제약: 일반 비서 확장성은 유지한다. 초기 일반 비서 기능의 구체적인 목록은 미정이다.

## DEC-003 — Mac mini 중앙 실행

- 날짜 / 상태: 2026-10-28 / 확정
- 결정: 첫 버전의 프로젝트 파일과 파일·명령 실행을 Mac mini에 둔다. MacBook과 모바일은 접속 클라이언트다.
- 검토한 방향: 중앙 실행, MacBook 등 여러 호스트의 Worker 동시 도입.
- 근거: 기기 전환과 실행 지속성을 우선 완성하고 초기 실행 환경을 단순화한다.
- 제약: 접속 종료와 작업 종료를 분리한다. 호스트 재부팅 시 프로세스의 무손실 복구를 보장하는 결정은 아니다. 외부 API 모델 추론은 공급자에서 이루어진다.
- 후속: Worker 연결 경계를 분리해 향후 원격 호스트 확장을 허용한다. 초기에는 분산 실행을 구현하지 않는다.

## DEC-004 — 개발 작업별 브랜치와 Git worktree

- 날짜 / 상태: 2026-10-28 / 확정
- 결정: 같은 프로젝트의 여러 개발 작업에 각각 브랜치와 worktree를 할당한다.
- 검토한 대안: 단일 폴더에서 브랜치 전환, 작업마다 별도 clone, 공유 저장소의 worktree.
- 근거: 기능 구현과 다른 버그 수정을 병행하면서 작업 파일을 분리한다. 사용자가 worktree 방식을 명시적으로 선택했다.
- 제약: worktree는 파일 작업 폴더를 분리하며 권한·프로세스·포트·DB를 격리하는 보안 장치는 아니다. 병합 충돌과 공유 자원 충돌은 별도로 처리해야 한다.
- 우선순위: 기능 구현이 주 작업이다. 자동 선점·스케줄링 정책이나 병합 순서를 고정한 것은 아니다.
- 미결정: 동시 실행 수, 기준 브랜치, 테스트 환경 분리, 병합 승인 세부 절차, 충돌 해결 및 worktree 정리 정책.

## DEC-005 — Git/GitHub 기반 코드 공유

- 날짜 / 상태: 2026-10-28 / 확정
- 결정: 실행용 프로젝트는 Mac mini의 iCloud 밖 로컬 경로에 두고, 코드 변경은 Git/GitHub의 커밋·브랜치·병합으로 공유한다.
- 검토한 대안: iCloud 파일 동기화, Git/GitHub 기반 변경 공유.
- 근거: 독립된 개발 작업의 변경을 검토하고 명시적으로 통합하기 위한 방향.
- 제약: GitHub는 파일의 실시간 동기화나 실행 상태 저장소가 아니다. 같은 Mac mini의 worktree 사이에서 Git 이력 공유에 GitHub 왕복이 필수인 것도 아니다.
- 상태 저장: 대화·실행·승인 상태는 Mac mini의 서비스가 관리한다. 현재 버전 1 JSON 파일에 저장하며 백업·복원 정책과 기능은 미완료다.
- 현재 조치(2026-10-29): 공유 원본은 보존하고 `~/Developer/personal-ai`에 독립 clone을 만들었다. 상태·worktree는 `~/.local/share/personal-ai`다. 심볼릭 링크·Git 공용 경로까지 공유 위치를 거부한다.

## DEC-006 — 작업 브랜치 자동 커밋·push, 사용자 승인 후 최종 병합

- 날짜 / 상태: 2026-10-28 / 확정
- 결정: AI는 작업 브랜치에 자동으로 커밋하고 해당 원격 작업 브랜치에 push한다. 최종 병합은 사용자가 승인한 뒤 진행한다.
- 검토한 방향: 커밋·push 단계마다 승인, 작업 브랜치 자동 저장·공유 후 최종 병합 승인, 테스트 통과 후 자동 병합.
- 근거: 사용자가 작업 진행의 자동화와 최종 통합의 직접 검토를 선택했다.
- 범위: 당시에는 향후 워크스페이스 제품의 동작 정책이며 기획 저장소에 즉시 커밋·push하라는 요청으로 해석하지 않았다. 2026-10-29 사용자가 이번 개발 브랜치의 커밋·push를 명시적으로 요청했으므로 해당 저장소 작업은 승인되었다.
- 제약: 작업 브랜치 push와 최종 통합을 구분한다. main 직접 push나 강제 push를 자동화 대상으로 확정하지 않았다.
- 미결정: 자동 저장 시점·빈도, PR 생성 여부, 병합 방식, 충돌 처리, 승인 후 코드 변경 시 재승인 규칙과 일반 명령 승인 범위.

## DEC-007 — 일반 메시지는 추가 지시, 별도 버튼으로 중단

- 날짜 / 상태: 2026-10-28 / 확정
- 결정: 일반 메시지는 추가 지시로 전달하고 진행 중인 실행을 자동 중단하지 않는다. 중단 버튼은 별도로 제공한다.
- 처리 방향: 현재 작업을 유지하면서 다음 처리 가능한 시점에 반영한다. 연결 도구가 실행 중 지시 반영을 지원하지 않으면 대기열에 넣고 상태를 표시한다.
- 검토한 방향: 새 메시지마다 실행 중단, 추가 지시와 명시적인 중단 요청 분리.
- 근거: 사용자가 일반 메시지와 중단 버튼을 구분하는 흐름을 선택했다.
- 제약: 지시 전달을 실제 반영으로, 중단 요청을 실제 중단 완료로 표시하지 않는다. 도구별 지원 범위를 검증해야 한다.
- 미결정: 여러 지시의 적용 순서·취소·수정, 중단 시 하위 프로세스와 대기 지시 처리, 파일 변경 보존 및 재개 방식.

## DEC-008 — 프로젝트 내부 의존성 자동 설치

- 날짜 / 상태: 2026-10-28 / 확정

- 검토한 방향: 모든 의존성 설치 승인, 프로젝트 내부 설치 자동·전역 및 시스템 변경 승인.

- 미결정: 패키지 관리자별 캐시·설치 스크립트의 권한 처리, 시스템 변경 감지·차단 방법 및 승인 유효 범위.

## DEC-013 — Tailscale HTTPS와 별도 앱 인증

- 날짜 / 상태: 2026-10-29 / 코드 구현·자동 검증, 실제 네트워크 활성화 승인 대기
- 결정: 앱과 OpenCode는 loopback으로 유지하고 Tailscale Serve의 TCP HTTP backend를 사용한다. 앱은 명시적인 HTTPS ts.net origin 한 개와 로컬 출처만 허용한다. 원격 Secure 쿠키와 로컬 쿠키·세션을 분리한다. 모든 쓰기 요청에 정확한 Origin을 요구하고 Funnel을 사용하지 않는다.
- 근거: 기존 중앙 실행 방향에 HTTPS·애플리케이션 인증을 구체화한다. Tailscale의 원본 Host 보존을 공식 소스에서 확인했다.
- 제약: 앱 로그인은 12시간, 서버 재시작 시 만료. 로컬 프로세스를 격리하는 보안 샌드박스는 아니다. tailnet grants/ACL·실제 단말·인증서 확인은 적용 단계에서 검증한다.
